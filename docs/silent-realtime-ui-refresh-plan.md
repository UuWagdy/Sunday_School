## 1. المطلوب والنتيجة التي يراها المستخدم

المزامنة الحالية قد تنجح في تحديث مصدر البيانات، بينما تظل بيانات الشاشة قديمة حتى الحفظ أو تغيير فلتر. المطلوب ربط كل واجهة تعتمد على البيانات بإشعارات التغيير، مع إعادة جلب البيانات في الخلفية وتطبيق النتيجة بهدوء.

عند تعديل بيانات من الجهاز نفسه أو جهاز آخر:

- تتحدث القوائم والعدادات والأسماء والاختيارات ونتائج التقارير المعروضة تلقائيًا.
- تظل البيانات السابقة مرئية أثناء الطلب، بما فيها نتيجة فارغة سبق تحميلها بنجاح.
- لا يختفي الجدول، ولا يظهر مؤشر تحميل يغطي الشاشة عند كل إشعار.
- لا تتغير الفلاتر أو نص البحث أو الفرز أو التبويب الفرعي أو مكان التمرير بسبب الإشعار.
- لا تُمسح مسودة غير محفوظة، ولا يُنقل التركيز من الحقل الذي يكتب فيه المستخدم.
- لا يحتاج المستخدم إلى حفظ وهمي أو تغيير فلتر أو مغادرة التبويب لرؤية البيانات الجديدة.
- إذا تعذر الجلب، تبقى آخر نتيجة صحيحة، مع حالة خطأ محدودة وواضحة وإمكانية إعادة المحاولة.

اسم الأسلوب: **Reactive UI + Silent Background Revalidation**. المقصود الاحتفاظ بنتيجة العرض أثناء إعادة التحقق؛ ليس إنشاء منظومة offline-first أو تخزين محلي جديد في وضع السيرفر.

## 2. تعليمات ملزمة قبل التنفيذ

1. اقرأ `AGENTS.md` وأي تعليمات فرعية في المسارات التي ستعدلها، واقرأ `specs/001-program-service-customization/plan.md` لفهم البنية. الوصف القديم في ذلك الملف عن عدم وجود backend لم يعد يعكس الكود الحالي؛ الكود الفعلي هو المرجع هنا.
2. **ممنوع تشغيل `flutter analyze` إطلاقًا**، مباشرة أو عبر سكربت أو وكيل آخر. لا تضعه ضمن التحقق النهائي. هذه تعليمات صريحة من صاحب المشروع، وتسبق أي خطة قديمة.
3. استخدم اختبارات Flutter محددة الملفات. يمكن استخدام `dart analyze` لملفات معدلة محددة فقط إذا كانت هناك حاجة فعلية. ممنوع استبدال المنع بتحليل شامل آخر.
4. توجد تغييرات محلية كثيرة وملفات غير متتبعة قبل بدء هذه المهمة، منها مجلدات السيرفر والمزامنة والأتوبيسات. سجّل الحالة قبل التنفيذ؛ لا تعمل reset أو clean أو checkout لإلغاء تغييرات، ولا تفترض أن كل diff من صنعك.
5. لا تعمل commit أو push أو نشر أو installer أو تغيير قاعدة فعلية ضمن هذه المهمة. قدّم العمل للمراجعة في مساحة العمل.
6. لا تغيّر schema أو migration أو بروتوكول السيرفر إلا إذا أثبت اختبار أن ذلك ضروري لهذه المشكلة، ودوّن السبب والحد الأدنى من التغيير. الإصلاح المتوقع أساسًا في ربط تحديث البيانات بالواجهة.
7. احتفظ بـFlutter وRiverpod وDrift وSignalR الحاليين. لا تدخل Bloc أو GetX أو Firebase أو Supabase أو مدير حالة موازٍ.
8. لا تبدّل قاعدة البيانات أو تعيد إنشاء `ProviderScope`/`MaterialApp`/`MainShell` لكل حدث مزامنة. ممنوع استخدام `UniqueKey` أو عداد تحديث على جذر الشاشات لإجبار إعادة إنشائها.
9. لا تستخدم polling دوريًا لكل شاشة، ولا `setState` مؤقتًا كل ثانية، ولا تأخيرًا ثابتًا لإخفاء سباق بيانات.
10. حافظ على RTL والنصوص العربية والصلاحيات والسلوك الوظيفي والطباعة الحالية. لا تنفذ إعادة تصميم شكلية أو إصلاحات جانبية لا تخدم المطلوب.
11. نفّذ المراحل بالترتيب وباختبار لكل مجموعة. إذا وُجدت تعليمات محلية تلزم التوقف عند مرحلة، اتبعها وسجّل ما بقي؛ لا تدّعِ اكتمال كل الشاشات.
12. هذه الوثيقة تفصيل تصميم وليست ضمانًا أن أرقام الأسطر والرموز لن تتغير. تحقق من كل رمز قبل تعديله؛ لا تنسخ API تخمينيًا.

## 4. النطاق: حصر كامل للشاشات والمكونات

الحصر الأولي أدناه يشمل **27 ملفًا** تحت `lib/screens` وقت كتابة الخطة. أعد تشغيل الحصر عند التنفيذ، وأضف أي شاشة أو مكون بيانات جديد؛ لا تسقط الملفات غير الموجودة في شريط التنقل الرئيسي.

رموز التنفيذ:

- **P**: عرض يعتمد بالفعل على provider؛ أصلح تبعياته وطريقة عرض previous data.
- **L**: نتيجة تحتفظ بها الشاشة محليًا؛ تحتاج اشتراكًا ذا معنى وloader صامتًا محميًا من السباقات.
- **D**: فيها مسودة أو إدخال؛ تحتاج حماية dirty state بالإضافة إلى تحديث البيانات المرجعية.
- **X**: واجهة تشغيلية؛ تتفاعل حسب وظيفتها ولا تعاد تهيئتها بسبب تغير البيانات.

## 5. التصميم المقترح وملكية التحديث

### 5.1 مسار موحد يستفيد من Drift

المسار المفضل، مع السماح بتعديل أسماء الملفات والرموز إذا وُجد بديل مكافئ مثبت:

```text
كتابة محلية ناجحة عبر Drift ────────────────────┐
                                               ▼
حدث SignalR بعد commit -> تطبيع أسماء -> إبلاغ Drift -> tableUpdates
                                               │
                                               ▼
                   منسق واحد يجمع الجداول ويحدد المجالات المتأثرة
                                               │
                           revisions/tokens مستقلة لكل مجال
                              ┌────────────────┴────────────────┐
                              ▼                                 ▼
                    provider يعيد الحساب              شاشة ببيانات محلية
                    ويحافظ على previous data           تطلب refresh صامتًا
                              └────────────────┬────────────────┘
                                               ▼
                         اعتماد آخر نتيجة صالحة لنفس الاستعلام والجلسة
```

ميزة هذا المسار أنه يخدم SQLite المحلي وأحداث السيرفر، بدل وجود آليتين غير متوافقتين. استعلامات Drift `watch()` يمكن استخدامها للمراجع البسيطة؛ لا يلزم تحويل كل استعلام ثقيل أو متعدد الخطوات إلى Stream.

**قاعدة الملكية:** لكل نتيجة عرض مالك واحد لإعادة الجلب. لا تجعلها في الوقت نفسه تستمع إلى `tableUpdates` مباشرة، وإلى revision، وإلى provider invalidation، وإلى trigger قديم. يجوز وجود قناة بيانات provider وقناة أوامر refresh، لكن تنتهيان عند scheduler واحد يمنع التكرار.

### 5.2 ملفات مقترحة ومسؤولياتها

| الملف المقترح | المسؤولية |
|---|---|
| `lib/sync/data_change_domains.dart` | أسماء المجالات، تطبيع أسماء الجداول، جدول التبعيات؛ منطق نقي قابل للاختبار |
| `lib/sync/data_change_coordinator.dart` | اشتراك واحد بقاعدة البيانات الحالية، تجميع الأحداث، إصدار revisions/dirty markers، تنظيف الاشتراك |
| `lib/utils/silent_refresh_controller.dart` | جدولة single-flight وpending، حدود التأخير، التعامل مع dispose؛ فقط الجزء المشترك فعليًا |
| `test/data_change_domains_test.dart` | تبعيات الجداول والتطبيع وwildcard |
| `test/data_change_coordinator_test.dart` | local/remote events والتجميع وإعادة ربط قاعدة البيانات |
| `test/silent_refresh_controller_test.dart` | السباقات وpending/failure/dispose |

الأسماء مقترحة وليست ملفات موجودة. لا تبنِ framework عام ضخم، ولا تخزّن نسخًا ثانية من كل بيانات المشروع داخل المنسق.

### 5.3 تهيئة المنسق وتجنب الدورات

1. المنسق يراقب **نسخة `AppDatabase` الفعلية**، ويستبدل اشتراكه إذا تبدلت القاعدة.
2. هَيّئه من موضع ثابت تحت `ProviderScope` مثل consumer تمهيدي عند جذر التطبيق، مع اختبار إقلاع. لا تجعله شرطًا لتكوين القاعدة نفسها إذا كان يعتمد عليها.
3. الكود الحالي يهيئ SignalR من database provider ويقرأ القاعدة عند تطبيق الأحداث؛ راجع مسار الاعتماد لتجنب إضافة دورة بين database/sync/coordinator.
4. لا تنشئ `AppDatabase()` جديدة داخل خدمة التحديث، ولا container منفصلًا؛ يجب أن تكون الإشعارات والقراءة على النسخة نفسها.
5. أنشئ الاشتراك مرة واحدة، ونظّفه عند dispose/تبديل المصدر. لا تنشئ subscriptions أو timers في `build()` دون lifecycle مضبوط.
6. `ref.listen` داخل widget build مسموح وفق آلية Riverpod، بشرط ألا يؤدي إلى side effects أثناء البناء الأول أو اشتراكات يدوية متكررة. استخدم API المثبتة للمستمعات في lifecycle الآخر.
7. لا تقرأ أو تعدّل `ref` بعد التخلص منه. أخّر نشر الحالة عند الحاجة وفق lifecycle الصحيح، واختبر أول frame وتبديل المصدر.

### 5.4 التعامل مع التنفيذ الحالي في SignalR

- احتفظ بإبلاغ Drift عبر `markTablesUpdated` أو `notifyUpdates` المكافئ المدعوم، مع اختبار أن المنسق يستقبل الحدث.
- انقل/وحّد جدول التبعيات بدل ترك قائمة `ref.invalidate` قديمة بالتوازي مع revisions جديدة لنفس البيانات.
- الاختيار الافتراضي: providers البسيطة تقرأ revision مجالها في build؛ الشاشات L تستمع إليه وتعيد جلب نافذتها. إذا اخترت invalidation مركزية بدل revisions للـproviders الحالية، وثّق ذلك واختبر previous data وعدم ازدواج الطلبات.
- اجعل `*` أو reconnect المؤكد يعلّم كل المجالات stale مرة واحدة. wildcard القادم من السيرفر يحتاج إلى إبلاغ كل جداول Drift المعروفة، حتى الاستعلامات التي تستخدم watch مباشرة.
- طبّع casing وأسماء schema/quotes حسب أسماء البروتوكول الفعلية. ابنِ المطابقة من `actualTableName` ومن الأسماء canonical في السيرفر؛ لا تستخدم fuzzy contains قد يطابق جدولًا آخر.
- إذا استلمت اسمًا غير معروف، سجّله تشخيصيًا بلا بيانات حساسة واستخدم fallback محافظًا يضمن عدم تجمد الشاشة، مع حد للتكرار. لا تتجاهله بصمت.
- لا تعتبر `timestampUtc` أو ساعة الجهاز ترتيبًا مضمونًا للأحداث. revisions محلية monotonically increasing، ولا تفترض أن sequence السيرفر ثابت بعد restart أو أن Event model يقرأه بالفعل.
- لا تتجاهل أحداث `sourceDeviceId` المطابق إلا إذا أثبتت اختبارات أن مسار الكتابة المحلي يغطي كل الجداول والنتائج. الأسهل دمج التكرار وإبقاء correctness.
- لا تعتبر الحالة `connected` وحدها دليلًا على نجاح handshake/الاشتراك. اختبر تلقي حدث حقيقي بعد الاتصال، وtrigger التعافي بعد تأكد جلسة SignalR، لا قبل ذلك. غيّر transport فقط عند ثبوت خلل مؤثر.
- حالة ribbon «متصل/متزامن» لا تعني أن آخر نتيجة شاشة نجحت؛ لا تحوّل فشل query إلى نجاح بمجرد وصول حدث.

### 5.5 الجداول والأحداث المحلية

- `tableUpdates` لا يصنع polling للقراءة، ويستفيد من إشعارات Drift عند الكتابة.
- تحقق من `customStatement` وraw SQL والـbatch والمعاملات: يجب تمرير `updates` أو إبلاغ الجداول صراحة عندما لا يستنتجها Drift.
- لا تنشر تحديثًا نهائيًا قبل commit ولا عند rollback. اختبر ذلك بدل افتراض أن كل raw write مُغطى.
- لا تجعل منسق العرض يكتب إلى القاعدة أو يعيد بث نفس الحدث إلى السيرفر؛ هذا يصنع حلقة مزامنة.
- قد يصل حدث محلي وحدث echo من السيرفر لنفس الكتابة. يمكن أن يتجاوز echo نافذة التجميع؛ يسمح بقراءة متابعة زائدة محدودة، ولا يسمح بحلقات أو طلب لكل صف.

## 6. خريطة التبعيات الواجب ترميزها واختبارها

هذه بداية محافظة **وليست قائمة SQL نهائية**. افحص joins وحقول الفلترة والـDTO لكل query وأضف تبعياته الفعلية. المجالات التالية أسماء تصميمية يجوز تغييرها.

| المجال | الجداول الأساسية أو المرجعية المؤثرة | أهم المستهلكين |
|---|---|---|
| `people` | Persons، Person_Services، Stages، Khoroses، Areas وشجرتها، Fathers، Services، Stage_Services، Khoros_Services، Jender، تعريفات/قيم الحقول المخصصة | قوائم الأشخاص والاقتراحات والكارنيهات والنقل وما يقرأ أسماء الأشخاص |
| `attendance` | Coming، Absent_Persons، Absent_Print، Adding، Credit، وتبعيات people، وVisitations إذا أثرت في query الافتقاد/الفلترة | الحضور وشبكته وملخصه |
| `behavior` | Coming وتبعيات الأشخاص والخدمات المستخدمة | درجات السلوك وتقارير السلوك/الترم |
| `visitation` | Visitations، Persons، Coming عند الفلترة بالحضور، المراجع والحقول والخدمات المستخدمة | الافتقاد وملخصه |
| `buses` | Bus_Drivers، Bus_Assignments، Coming للانصراف، Persons، Stages، Khoroses، Areas، وأي مراجع يعرضها DTO | السائقون والطلاب والأعداد |
| `areas/stages/khoros/fathers/services` | جدول المجال وروابطه والجداول الداخلة في labels/counts الفعلية | القوائم المرجعية ونماذج الإدارة |
| `fields` | custom field definitions والقيم عندما يعرضها المستهلك | تعريف الأعمدة والفلاتر وPersonDialog والكارنيهات |
| `family` | Family_Relationships، Persons ومراجع query/الحقول | عرض العلاقات وملخص الشخص |
| `documents` | person documents، وتبعيات الاسم/الشخص إذا عُرضت | مستندات الشخص وتفاصيله |
| `tayo` | Tayo_Cards، Person_Tayo_Points، وتبعيات الأسماء والخدمات/الحقول والفلاتر الفعلية | كل تبويبات الطايو والرصيد والسجل |
| `settings` | Settings | الهوية، الكارنيهات، الاجتماعات، الرهوط، الصندوق، رسائل الافتقاد، وإعدادات الطايو الفعلية |
| `analytics/reports` | اتحاد جداول query الخاص بكل نتيجة، لا كل جداول المشروع عشوائيًا | الرسوم والإحصاء والمقارنة وتقفيل الترم والتقارير |
| `access` | Pass، User_Permissions_Ext، User_Visibility_Filters | auth والمستخدمون وقيود رؤية البيانات في جميع المجالات |

تعريفات الحقول والمستندات لديها أسماء جداول مولدة؛ استخرج الاسم من `actualTableName`/generated database بدقة. لا تفترض اسم Dart class هو اسم SQL.

### 6.1 تفاصيل تبعيات يسهل نسيانها

1. إعادة تسمية مرحلة/خورس/منطقة/أب اعتراف يجب أن تجدد صف الشخص الذي يعرض الاسم، حتى لو لم يتغير جدول Persons.
2. تغير hierarchy المناطق قد يغير نطاق الفلتر لا label فقط؛ أعد حساب descendants قبل اعتماد الاستعلام الجديد.
3. تغير Stage_Services/Khoros_Services قد يغير أهلية الخدمة والاقتراحات والتقارير، حتى إذا كان تحديث Person_Services لاحقًا أو ليس مصدر query.
4. تغير CustomFieldDefinitions قد يغير الأعمدة والفلاتر، وتغير القيم قد يضيف/يخرج أشخاصًا من النتائج.
5. تغير Coming قد يغير الحضور والسلوك والطايو إن كان query يعتمد عليه والافتقاد والأتوبيسات والتحليلات؛ استند للكود الفعلي لكل مستهلك.
6. إبطال repository wrapper لا ينفّذ تلقائيًا future سبق استدعاؤه وحُفظت نتيجته داخل الشاشة.
7. أحداث Settings لا تحمل key في البروتوكول الحالي؛ أعد قراءة مفاتيح الشاشة ذات الصلة وقارن القيم الفعلية، ولا تمسح كل مسودات الإعدادات.
8. تغير الصلاحيات يجب أن يعيد تقييم نطاق الرؤية. ليس مجرد label update؛ انظر الاستثناء الأمني في القسم 10.

## 7. عقد التحميل لكل شاشة

كل شاشة أو provider يعرض بيانات يجب أن يميز بين الحالات التالية، سواء باستخدام model مشترك أو state محلية واضحة:

| الحالة | السلوك المرئي |
|---|---|
| أول تحميل بلا نتيجة سابقة | مؤشر تحميل أولي مناسب |
| نتيجة جاهزة | عرض النتيجة، حتى لو كانت القائمة فارغة |
| إعادة تحقق في الخلفية | عرض آخر نتيجة كما هي؛ لا overlay ولا تعطيل لكل الشاشة |
| نجاح بخانات/صفوف متغيرة | اعتماد نتيجة جديدة بهويات مستقرة مع حفظ حالة المستخدم |
| فشل مع نتيجة سابقة | إبقاء النتيجة، وتوضيح أنها قديمة عند الحاجة مع retry محدود |
| فشل أول تحميل | خطأ واضح مع إعادة محاولة؛ لا spinner أبدي |
| نتيجة ممنوعة/انتهت الجلسة | منع العرض/الإجراءات فور تأكد ذلك؛ لا الاحتفاظ ببيانات غير مصرح بها |

لا تستخدم `items.isEmpty` وحدها لمعرفة أول تحميل. أضف `hasLoaded/hasSnapshot` صريحًا أو metadata موثوقة؛ النتيجة الفارغة الصحيحة ليست حالة انتظار.

### 7.1 عند تعديل loader موجود

- افصل initial/query-change عن background-revalidate؛ لا توصل الحدث بدالة تمسح القائمة أو تصفر العدادات أو الحقول.
- يُسمح بمشاركة fetch logic، لكن side effects واجهة أول التحميل تختلف عن الصامت.
- اجلب النتيجة إلى متغيرات مؤقتة، ولا تعدل القائمة المعروضة تدريجيًا أثناء انتظار بقية الاستعلامات.
- احتفظ بالبيانات والملخص القديمين حتى اكتمال حزمة النتيجة الجديدة. إذا فشل جزء أساسي، لا تخلط ملخصًا جديدًا بقائمة قديمة وتصفهما كمتسقين.
- تزامن استعلامين في `Future.wait` لا يضمن snapshot واحدة من قاعدة البيانات. استخدم قراءة transaction مناسبة عندما تتطلب الدقة ذلك وتدعمها البنية، أو وثّق eventual consistency وأعد التحقق بعد الأحداث اللاحقة.
- استخدم معرف request متزايدًا؛ لا تعتمد على `millisecondsSinceEpoch` لتفادي تصادم طلبين في نفس المللي ثانية.
- افحص `mounted`/صلاحية controller والجلسة قبل كل تطبيق نتيجة وبعد كل await ذي صلة.
- لا تمسح الخطأ وتسمي النتيجة ناجحة إلا عند جلب ناجح فعليًا.

### 7.2 previous data في Riverpod

- إعادة حساب provider لا يجب أن تجعل child يستبدل الجدول كله بـspinner إذا كانت هناك نتيجة سابقة لنفس query ونفس نطاق الوصول.
- راجع الفرق بين refresh وreload في `AsyncValue`، وطريقة تعامل الكود الحالي مع `when` و`asData` و`.value` وفق النسخة المثبتة.
- `skipLoadingOnRefresh` وحده لا يضمن معالجة recompute الناتج عن تغير dependency؛ اختبر مسار reload أيضًا، أو افحص وجود بيانات سابقة صراحة.
- لا تعِد `[]` مؤقتًا لمجرد أن auth في loading ثم تعتمدها كنتيجة حقيقية؛ هذا قد يمسح الشاشة ويستبدل snapshot صحيحة.
- previous data تخص query وهوية جلسة ونطاق صلاحيات محددة؛ لا تعرض نتيجة فلتر قديم على أنها نتيجة فلتر جديد.
- لا تكتب يدويًا في ملفات `.g.dart`. إن تغيرت annotations استخدم codegen المحدد ثم راجع diff.

## 8. منع السباقات وفقد الأحداث

يجب تنفيذ واختبار القواعد التالية قبل تعميم الحل على الشاشات.

### 8.1 بيانات التحكم المطلوبة معنويًا

```text
queryKey: نسخة ثابتة من الفلاتر/الفترة/الفرز/الخدمة/المستخدم المؤثر
sourceEpoch: يتغير عند تبديل القاعدة/السيرفر/الجلسة/نطاق الصلاحيات
queryGeneration: يتغير عند تغيير query المقصود أو إبطاله
requestedRevision: أحدث تغيير بيانات يجب أن تغطيه النتيجة
appliedRevision: آخر revision غطتها نتيجة ناجحة
inFlight: هل هناك fetch لهذا المستهلك؟
pending: هل وصل طلب إضافي أثناء الجلب؟
disposed: هل انتهى عمر المستهلك؟
```

لا يجب أن تكون هذه الحقول حرفيًا متفرقة في كل widget؛ المهم أن تتحقق invariants وتكون قابلة للاختبار. انسخ القوائم/maps ضمن query snapshot حتى لا تتغير أثناء await.

### 8.2 خوارزمية الجدولة الملزمة

1. حدث مرتبط يرفع revision ويعلم المستهلك stale.
2. اجمع الأحداث في نافذة قصيرة موحدة. الموجود نحو 80ms؛ قيمة بداية مناسبة 80–150ms تُقاس وتوثّق.
3. أضف حد انتظار أقصى، مثل 500ms، حتى لا يمنع تدفق مستمر من الأحداث التحديث للأبد. تجنب debounce trailing بلا حد.
4. إن كان المستهلك غير ظاهر أو توجد write حرجة تحمي مسودة، اكتفِ بـpending/stale ثم أعد الجدولة عند إتاحة العرض/انتهاء العملية.
5. إن كان fetch جارٍ، سجّل pending وأحدث revision؛ لا تبدأ fetch مماثلًا متوازيًا ولا تتجاهل الحدث.
6. عند بدء fetch التقط query/source/generation/revision ثابتة.
7. عند اكتماله، طبّق النتيجة فقط إذا كان المستهلك حيًا، والجلسة/المصدر/query/generation ما زالت مطابقة.
8. إذا وصل revision أحدث أثناء الجلب، يمكن عرض النتيجة الوسيطة الصالحة لنفس query، لكن اترك stale/pending وابدأ متابعة واحدة تغطي آخر revision. لا تدع appliedRevision يقفز لأحدث revision لم يقرأه الطلب.
9. بعد النجاح، إذا تغيرت query شغّل query الحالية؛ وإذا بقي pending لنفسها شغّل متابعة مجمعة.
10. بعد الفشل، احتفظ بـstale وبالبيانات. لا تدخل حلقة retry فورية في finally بسبب pending نفسه. أعد المحاولة بتراجع زمني محدود أو عند حدث جديد/استعادة الاتصال/طلب المستخدم.
11. بعد dispose لا timers ولا إعادة جدولة ولا setState ولا قراءة ref قديم.
12. عند تغيير sourceEpoch، اعزل النتائج القديمة حتى لو كانت HTTP غير قابلة للإلغاء فعليًا.

### 8.3 ترتيب fetch بالنسبة للكتابة

- نجاح حفظ/نقل/إضافة يحتاج أثرًا مرئيًا حتى لو تأخر echo أو انقطع socket.
- funnel نجاح الكتابة والإشعار البعيد إلى scheduler نفسه، أو أثبت أن Drift المحلي ينشر الحدث بعد النجاح.
- لا تحول background refresh إلى إعادة حفظ تلقائية.
- إذا تغيرت مسودة أثناء تنفيذ save، نجاح ذلك save لا يحق له اعتبار التعديلات الأحدث محفوظة. قارِن نسخة المسودة التي أرسلتها مع الحالية قبل إزالة dirty state.
- لا تعِد إنشاء repository notifier وهو في منتصف write لمجرد أن حدثًا تابعًا لنفس الكتابة وصل؛ افصل جلب العرض عن هوية مالك العملية أو أثبت سلامة lifecycle بالاختبار.

## 9. الصفحات والفرز والتحديد والتمرير

### 9.1 الصفحات المحملة

الحل السهل الخاطئ هو استدعاء تحميل الصفحة الأولى بعد كل حدث. هذا يرجع المستخدم إلى البداية ويُسقط ما حمّله.

العقد المطلوب للقوائم المقسمة إلى صفحات:

1. احتفظ بعدد النافذة المحملة الحالية وحدها الطبيعي، وليس كل قاعدة البيانات.
2. عند refresh صامت، اجلب نافذة من البداية بطول الصفوف المحملة/سعة الصفحات الحالية وفق قدرة repository، مع العدد الكلي والفرز والفلاتر نفسها.
3. إذا كانت query تستخدم raw pagination/فلترة لاحقة، اشتق `offset/hasMore` من cursor أو offset الفعلي للمصدر، لا من عدد الصفوف المرئية فقط. راجع خصوصًا الحضور و`onHasMore`.
4. لا تدع load-more قديمًا يلحق صفوفًا من generation سابقة بعد إعادة تحميل النافذة.
5. اختر تسلسلًا واحدًا: انتظار load-more ثم revalidate معلق، أو إبطال جيله ومنع اعتماده ثم إعادة النافذة. غطِّ الاختيار باختبار.
6. اجعل الترتيب حتميًا مع tie-breaker بالـID عند تساوي عمود الفرز إن لم يكن موجودًا، دون تغيير اختيار المستخدم للفرز.
7. اجعل IDs فريدة بعد الدمج. لا تُبقِ نسخة محذوفة مع نسخة أحدث أو تكرر صفًا بين الصفحات.
8. بعد الحذف أو خروج صف من الفلتر، تتقلص النافذة طبيعيًا أو تُملأ من الصفوف التالية وفق query؛ حدّث offset/count/hasMore معًا.
9. لا تحوّل تحديثًا صغيرًا إلى `fetchPersons(limit: null)` على كل حدث. الاستخدام غير المحدود فقط للشاشات التي تتطلب ذلك أصلًا وبحدود أداء مقاسة.

### 9.2 التحديد

- خزّن التحديد بالـID وليس بمرجع DTO أو index، واستخدم `ValueKey(entityId)` للصفوف المناسبة.
- أبقِ IDs المختارة التي لا تزال صالحة؛ لا تمسح الكل عند إشعار.
- اختفاء صف من النافذة لا يعني حذفه من قاعدة البيانات. حافظ على سياسة التحديد الحالية: إذا كان التحديد لكل النتائج، لا تعمل intersection مع الصفحة المرئية فقط.
- عند عملية جماعية، أعد التحقق من صلاحية IDs وفق النطاق الحالي قبل الكتابة؛ لا تعتبر snapshot قديمة ضمانًا.
- إذا كان التحديد محصورًا في النتائج المرئية حاليًا، وثّق القاعدة وحدّث العدد دون اختيارات مخفية غير مفهومة.

### 9.3 التمرير والهوية البصرية

- احتفظ بـScrollController والمفاتيح المستقرة. لا تعِد بناء controllers لكل حدث أو تضع key مرتبطًا بـrevision.
- حفظ pixels وحده لا يحفظ نفس المحتوى إذا أضيف صف قبل موضع المستخدم. فضّل anchor بالـID وموضعه النسبي حيث يمكن تطبيقه دون اعتماد جديد كبير.
- الحد الأدنى المقبول: لا قفزة للأعلى، clamp آمن إذا قصر المحتوى، وثبات الصف المرئي عند إدراج صفوف قبله في اختبارات القائمة الأساسية. إذا تعذر anchor لقائمة معينة، وثّق القيد بوضوح ولا تدّعِ حفظ الموضع بالكامل.
- احتفظ بالتمرير الأفقي والعمودي لشبكة الحضور والجداول العريضة.
- لا تعمل jumpTo قبل وجود clients/أبعاد صالحة أو بعد dispose. لا تعارض حركة تمرير يقوم بها المستخدم أثناء الجلب.
- تحديث نفس النص أو نفس القائمة منطقيًا لا يحتاج remount أو animation دخول للجدول كله. لا تقارن DTOs بالمرجع فقط إذا كانت instances جديدة في كل طلب.

## 10. حماية الإدخال والتعارضات وتغير الصلاحيات

### 10.1 افصل البيانات عن المسودة

كل نموذج أو جدول editable يحتاج تمييزًا واضحًا بين:

- `baseline`: آخر قيم محفوظة بُني عليها التحرير.
- `draft`: قيم المستخدم الحالية.
- `remote/current`: أحدث قيم جرى جلبها.
- `dirtyFields/dirtyIds`: ما تغير محليًا ولم يُحفظ، مع نسخة/جيل للتعديل.

عند وصول بيانات جديدة:

1. حدّث القوائم المرجعية وبيانات العرض غير المعدلة.
2. حدّث الحقول النظيفة فقط إذا كان ذلك آمنًا ولا يحرك cursor أو selection النص.
3. لا تعِد إنشاء TextEditingController أو تغيير `.text` لحقل dirty أو نشط كل مرة.
4. إذا تغير نفس الحقل/السجل بعيدًا، احتفظ بالمسودة واعرض تنبيهًا صغيرًا مستقرًا مثل «فيه تغييرات أحدث للبيانات دي». لا تفتح modal تلقائيًا لكل حدث.
5. عند محاولة الحفظ، أعد قراءة baseline اللازم إذا عُرف تعارض، واطلب قرارًا واضحًا وقت الحفظ/التحميل. لا تعمل last-write-wins صامتًا لمجرد أن الواجهة اتحدثت.
6. إذا حُذف الكيان الجاري تحريره، احتفظ بالنص للنسخ أو الإلغاء وأوقف حفظه كأنه موجود. لا تعيد إدراجه تلقائيًا.
7. حين ينتهي التحرير بالحفظ/الإلغاء، نفّذ refresh معلقًا واحدًا يغطي آخر revision.
8. تبديل الفلتر أو الفترة بإرادة المستخدم يتبع سياسة المسودة الحالية؛ لا تمسحها كأثر جانبي لإشعار خارجي.

### 10.2 حالات خاصة إلزامية

| الموضع | قاعدة الحماية |
|---|---|
| السلوك | لا تستدعِ `_onSearch()` الحالية على الإشعار؛ افصل درجات السيرفر عن dirty score لكل شخص. اجلب الدرجات للـquery المنفذة، وادمج غير المعدل فقط. default السلوك الحالي 5 يبقى كما هو |
| الصندوق | أعد مزامنة controller للحقل النظيف فقط، وتخلص من controller المحذوف عندما لا يكون تحريره نشطًا. الإجماليات تعتمد model محددًا لا خليط قيم controllers/remote مجهولة. الحقل الجاري تحريره لا يتغير تحت يد المستخدم |
| الاجتماعات/الرهوط/الصندوق | التخزين JSON aggregate داخل Settings قد يسبب overwrite لتغييرات جهاز آخر. أعد قراءة القيمة قبل الحفظ عند معرفة التعارض؛ ادمج العناصر فقط إذا لها هوية مستقرة مثبتة، وإلا اعرض قرارًا صريحًا. لا تختلق merge بالـindex |
| مصمم الكارنيه | لا تعِد `_loadSettings()` بما ينسخ قالب السيرفر فوق التصميم dirty. حدّث أسماء/بيانات الأشخاص، وأعلِم عن قالب أحدث دون تطبيقه قسرًا |
| الرهوط | لا تشغل `_generateGroups()` على حدث؛ التوزيع العشوائي عمل يطلبه المستخدم، وليس refresh. المجموعة غير المحفوظة مسودة مستقلة |
| PersonDialog | قوائم اختيار تفاعلية مع draft ثابتة؛ تغيّر الخيارات لا يعيد تعيين المنطقة أو الخدمة لأول عنصر. IDs المحذوفة تُعرض كاختيار غير متاح وتُراجع عند الحفظ |
| المستخدمون والخدمات والمراحل والخوارس | تجدد القائمة دون استدعاء دالة تحميل الصف إلى نموذج التحرير كلما provider تغير |
| ملاحظات الحضور والطايو | تبقى الملاحظات والكمية/النقاط المختارة كما هي؛ حدّث التاريخ/السجل المحفوظ دون إعادة إرسال عملية المستخدم |
| النقل والعمليات الجماعية | أي preview قديم يُعاد التحقق منه قبل التنفيذ. الإشعار لا ينفذ نقلًا أو حذفًا أو حفظًا تلقائيًا |

هذه المهمة تحمي المسودة وتكشف التعارض المعروف. **لا تعد بضمان منع كل lost update بين أجهزة متزامنة** إذا كانت API لا تدعم version/CAS/ETag. مقارنة القراءة ثم الكتابة لا تكون atomic؛ دوّن هذا القيد وأي اقتراح لاحق منفصل بدل ترحيل schema/إعادة بناء backend دون ضرورة.

### 10.3 استثناء الصلاحيات والجلسة

- الاحتفاظ بالبيانات أثناء refresh مخصص لنفس المستخدم والمصدر ونطاق الوصول.
- إذا تغير المستخدم/خرج من الجلسة/تبدل مصدر البيانات، امنع تطبيق النتائج القديمة وأزل البيانات الخاصة بالسياق السابق.
- عند ثبوت سحب صلاحية أو تضييق visibility، امنع الإجراء والبيانات خارج النطاق؛ لا تجعل شرط «بدون وميض» سببًا للاحتفاظ بها.
- إذا كان تغير الصلاحيات متعلقًا بمستخدم آخر فقط، لا تمسح كل واجهات المستخدم الحالي دون سبب. افحص الأثر الحقيقي، مع احترام أن الحدث قد لا يحمل IDs.
- في `main_shell.dart` حافظ على الوجهة الحالية بهوية مستقرة عند تغير قائمة الصلاحيات، لا numeric index وحده. إذا أزيل تبويب قبل الحالي، لا تنقل المستخدم إلى شاشة مختلفة بالصدفة.
- إذا أصبح التبويب الحالي غير مسموح، انتقل لوجهة مسموحة أو fallback مناسب؛ هذا انتقال مشروع وليس خطأ حفظ حالة.
- راجع `auth_service.dart::refreshUser()` عند تكامل هذا المسار: لا تدخل loading يمسح الجلسة لكل تحديث بيانات، ولا تجعل فشل قراءة صلاحيات يعني نجاح التحديث. أي توسيع لتعامل حذف المستخدم/انتهاء الجلسة يكون محدودًا وموثقًا.

## 11. التقارير والتحليلات والطباعة

1. شاشات البحث اليدوي يجب أن تفصل **draft filters** عن **lastExecutedQuery**. refresh يعيد آخر query أنتجت النتيجة، وليس قيم فلاتر لم يضغط المستخدم بحثها بعد.
2. قبل أول بحث في تقرير/مقارنة/تقفيل ترم، جدّد الاختيارات فقط. لا تنفذ تلقائيًا تقريرًا مكلفًا لم يطلبه المستخدم.
3. بعد وجود نتيجة، يحدّث الحدث المرتبط هذه النتيجة صامتًا باستخدام آخر query منفذة.
4. في Dashboard حدّث كل family instance ظاهرة بمعاملاتها، ولا تفترض أن provider غير parameterized يغطيها. استخدم تبعيات خاصة بكل رسم لتجنب إعادة حساب كل شيء عند جدول غير مرتبط.
5. في `TermAttendanceClosureWidget` افصل دالة الحساب عن UI الزر والحالة `_isLoading`، واحفظ خيارات الدرجات والسلوك والخدمات والفترة وموضع الجدول.
6. في Reports لا تنشئ future توليد PDF جديدة في كل build. خزّنها/اجعلها provider keyed بـquery وdata revision ذات صلة، واجمع التحديثات.
7. معاينة PDF المعروضة تتحدث بعد اكتمال البيانات ذات الصلة وبمعدل محدود، مع الاحتفاظ بالمعاينة السابقة حتى جاهزية الجديدة. امنع نتيجة PDF قديمة من استبدال أحدث واحدة.
8. فرّق بين live preview وبين export/print بدأت بالفعل: خذ snapshot ثابتة للملف الجاري توليده، ولا تُلغِ الطباعة أو تفتح print dialog جديدًا عند حدث.
9. حدث جداول غير مرتبطة يجب ألا يعيد توليد PDF. حدث جديد أثناء التوليد يؤدي إلى متابعة واحدة إذا كانت المعاينة ما زالت مفتوحة، لا توليد متوازٍ غير محدود.
10. لا تغيّر حساب السلوك أو أهلية الخدمات أو تنسيق ملفات التصدير تحت عنوان تحديث صامت؛ اختبر عدم تراجعهما.

## 12. الاتصال والعودة للتطبيق والشاشات غير الظاهرة

- انقطاع الاتصال لا يمسح آخر بيانات في الذاكرة ولا المسودة. اعرض الحالة العامة في ribbon أو مؤشر محدود حسب الموجود.
- نجاح reconnect مؤكد يسبب catch-up لجميع المجالات مرة واحدة، لأن أحداثًا قد تكون فُقدت. لا تفترض وجود replay/checkpoint دائم في البروتوكول الحالي.
- تبديل Local/Server أو عنوان السيرفر أو استعادة قاعدة نسخة جديدة يغير sourceEpoch؛ لا تعرض نتائج المصدر السابق على أنها الحالية.
- عند app resume أو عودة الشاشة للظهور: تحقق من stale/revision وجلسة الاتصال ونفذ catch-up واحدًا عند الحاجة، دون فتح اتصال إضافي لكل شاشة.
- افحص طريقة عرض MainShell الحالية: هل الشاشات تُهدم عند التنقل أم محفوظة داخل stack؟ لا تغيّر navigation strategy كلها لتنجز هذه المهمة.
- الشاشة المحفوظة لكنها غير ظاهرة لا تشغّل queries/PDF ثقيلة لكل حدث؛ علّمها stale وحدّثها عند إظهارها. مجرد `mounted` لا يعني أنها ظاهرة.
- Riverpod 3 له سلوك pause للمستهلكين غير الظاهرين؛ اختبر التصميم على النسخة المثبتة، ولا تفترض أن listener أو timer خاص يتوقف تلقائيًا.
- الشاشة التي تُنشأ من جديد تجلب snapshot حالية عبر مسارها الطبيعي؛ لا تحتاج تخزين كل بيانات كل الشاشات عالميًا.
- احتفظ بـdirty revision مستقل عن حالة fetch، بحيث لا تضيع أحداث وصلت في الخلفية أثناء pause أو غياب المستمع.
- إذا لم يكن إيقاف queries للشاشات الخفية ممكنًا بلا تغيير تنقل كبير، وثّق الحل المحدود وحدوده واختبر منع تضاعف الاشتراكات؛ لا تخفِ حملًا مستمرًا تحت ادعاء «صامت».

## 13. الأداء والتشخيص دون إزعاج المستخدم

### 13.1 حدود أداء مستهدفة

- هدف في شبكة محلية مستقرة وquery خفيفة: ظهور التغيير خلال نحو ثانية من وصول الحدث، وليس وعدًا ثابتًا لكل تقرير/شبكة.
- تجميع الأحداث يبدأ تقريبًا 80–150ms وله حد انتظار أقصى. قِس قبل إضافة debounce ثانية في كل طبقة.
- لكل query/مستهلك fetch واحد جارٍ؛ الدفعة أثناءه تنتج متابعة واحدة تغطي revisions الأخيرة.
- لا fetch لكل صف في UI refresh، ولا تحميل كل الأشخاص عندما تكفي النافذة المحملة.
- لا update لكل Provider في المشروع عند أي جدول. wildcard مخصص للتعافي/حدث شامل لا للإشعار المعتاد.
- لا rebuilding لجذر التنقل/الكاميرا/المصمم بسبب بيانات لا تخصه. هذا لا يعني منع كل rebuild؛ المقصود ثبات state وهوية العناصر المهمة.
- استخدم query/source/revision مشتركة لتجنب تكرار نفس القراءة بين مكونات متطابقة إذا أثبت القياس الحاجة؛ لا تبنِ cache عامة غير مطلوبة.

### 13.2 تشخيص قابل للمراجعة

في debug أو test سجّل بشكل محدود:

- نوع المصدر local/remote/reconnect/resume.
- أسماء الجداول والمجالات المتأثرة بعد التطبيع.
- request ID وquery generation/source epoch وrevision المستهدفة.
- بدأ fetch/نجح/فشل/أهملت نتيجة قديمة/وجد pending.
- زمن الطلب وعدد استدعاءات query في سيناريو الدفعات.

لا تسجّل SQL arguments الشخصية أو كلمات المرور أو JWT أو ملاحظات الأشخاص أو صورهم. لا تستخدم SnackBar نجاح لكل حدث، ولا أخطاء متكررة كل 80ms أثناء انقطاع واحد. التفاصيل التقنية للتشخيص، والرسالة للمستخدم عربية ومختصرة.

## 14. مراحل التنفيذ بالتسلسل

كل مرحلة لها نتيجة قابلة للمراجعة. لا تعتبر إنشاء utility وحده إنجازًا لتحديث كل التبويبات.

### المرحلة A — حصر فعلي وخط أساس

- [ ] اقرأ التعليمات وسجّل `git status --short` وdiff البداية بدون تعديل ملفات المستخدم.
- [ ] احصر `lib/screens` والمكونات والحوارات والـproviders وكل `_load/_fetch/FutureBuilder/get/watch` ذات صلة.
- [ ] أنشئ `docs/silent-ui-refresh-implementation-report.md` مبكرًا وابدأ matrix لكل ملف: المصدر، التبعيات، loader، dirty policy، الاختبارات.
- [ ] أثبت بفحص/اختبار أن إبطال Persons baseline لا يغير `_allPersons`، وأن loaders الحالية تمسح بياناتها.
- [ ] افحص أسماء الجداول الفعلية وبث commit وتحديثات raw writes وتهيئة SignalR ووضع Local.
- [ ] دوّن أي فرق عن هذه الخطة. لا تعمم استنتاجًا من شاشة واحدة على الباقي.

**بوابة المرحلة:** حصر بلا ملفات مفقودة، تفسير واضح لمسار التغيير الحالي، baseline محمي.

### المرحلة B — المنسق والتبعيات والجدولة

- [ ] نفّذ التطبيع والمجالات وخريطة الجداول بمنطق قابل للاختبار.
- [ ] نفّذ تهيئة المنسق مرة واحدة، واشتراك database الصحيح والتنظيف عند تبديل المصدر.
- [ ] وحّد SignalR/Drift/local success مع إزالة ownership المزدوج دون قطع المسار القائم.
- [ ] نفّذ single-flight وpending وgeneration/epoch وfailure policy وحد التجميع الأقصى.
- [ ] اختبر local + remote + wildcard + reconnect + unknown table + disposal + continuous events.
- [ ] اختبر الإقلاع وتبديل القاعدة/المصدر وعدم إغلاق قاعدة قيد الاستخدام بسبب حدث عادي.

**بوابة المرحلة:** لا تضيع أحداث أثناء fetch، لا حلقات، لا database recreation لكل إشعار.

### المرحلة C — نموذج مرجعي للأشخاص والحضور

- [ ] افصل silent refresh عن loaders التي تمسح البيانات؛ شارك query construction دون مشاركة reset UI.
- [ ] حافظ على نافذة الصفحات والفرز والعدد/الملخص والتحديد والتمرير.

## 15. خطة الاختبارات السلوكية

الاختبارات هنا مبررة لأن التغيير متزامن وعابر للشاشات؛ لا تكتب اختبارات تعكس أسماء الدوال فقط أو تكتفي باستدعاء `setState`.

### 15.1 اختبارات المنطق والتنسيق

| السيناريو | النتيجة المطلوبة |
|---|---|
| إعادة تسمية Areas/Stages/Fathers/Khoroses | revision query الأشخاص/القوائم التابعة ترتفع دون انتظار حدث Persons |
| Coming يتغير | تحديث الحضور والسلوك والأتوبيسات/الافتقاد/التقارير التي تعتمد عليه فقط |
| اسم جدول بحروف مختلفة/اسم canonical | تطابق دقيق مع الاسم الفعلي؛ لا false match |
| wildcard أو unknown fallback | كل المجالات اللازمة تصبح stale، وDrift watchers لا تفوت الإشعار |
| تعديل SQLite محلي | المنسق يرى الحدث دون اتصال SignalR |
| write raw مع تصريح الجداول | يظهر بعد النجاح/commit، ولا نتيجة اعتماد نهائي من rollback |
| 100 حدث في دفعة قبل بدء fetch | عدد الجلب قريب من دفعة واحدة لكل مستهلك مرتبط، لا 100 |
| حدث أثناء fetch | follow-up واحدة على الأقل تغطي أحدث revision؛ لا إسقاط بسبب inFlight |
| أحداث مستمرة | تحديث يحصل خلال الحد الأقصى للتجميع؛ لا starvation |
| response قديمة بعد تغيير الفلتر | لا تطبق على query الجديدة |
| response قديمة بعد logout/تبديل مصدر | تُهمل، حتى لو الكيان له ID مطابق في المصدر الجديد |
| فشل مع pending | بيانات قديمة + stale، ولا loop فورية لا نهائية |
| dispose/toggle source مرات | الاشتراكات القديمة ملغاة، لا timers متروكة أو ref disposed errors |
| نفس query بلا تغير فعلي | لا reset للحالة أو controllers أو أفعال جانبية |

استخدم `Completer` وfake clock/scheduler أو ضخ الوقت في اختبارات Flutter بدل sleeps عشوائية. لا تفترض ترتيب الشبكة طبيعيًا؛ أكمل futures بالعكس عمدًا.

أضف أوامر بقية الاختبارات المناسبة للملفات التي أنشأتها/عدلتها، وشغّلها في مجموعات واضحة. إذا لا يوجد Flutter في PATH، ابحث عن SDK المستخدم محليًا قبل إعلان تعذر الاختبار. لا تثبت SDK/حزم عشوائية لمجرد ذلك.

```powershell
# مثال فقط: مرّر إلى format الملفات التي عدلتها أنت لهذه المهمة.
```

لا تشغّل format على `lib/` أو المشروع كله. لا تعمل codegen شاملًا بلا حاجة، ولا تعدّل generated files يدويًا. إذا كان build_runner لا يدعم filter المذكور أو ولّد مخرجات إضافية، استخدم المسار المدعوم وراجع جميع المخرجات دون حذف تغييرات المستخدم.

## 18. مخرجات Gemini المطلوبة وبرومبت المراجعة

### 18.1 ملفات التسليم

1. تنفيذ متكامل ضمن النطاق، أو تصريح واضح بالجزء المتبقي إذا وُجد مانع حقيقي.
2. `docs/silent-ui-refresh-implementation-report.md` يحتوي:
   - baseline: ما كان متغيرًا قبل المهمة، وكيف ميزت تعديلاتك عنه، وأي baseline لم تتمكن من حفظه.
   - التصميم النهائي الفعلي ومالك refresh لكل مسار، وأي انحراف عن هذه الخطة وسببه.
   - قائمة الملفات المضافة/المعدلة **لهذه المهمة فقط** مع وظيفة كل مجموعة.
   - matrix لكل الشاشات الـ27، والمكونات/التبويبات الداخلية والحوارات، مع حالة تنفيذ/فحص/استثناء مبرر.
   - خريطة التبعيات النهائية، ومسار local/remote/reconnect/resume/access/settings.
   - سياسة السباقات والصفحات والتحديد والتمرير والمسودات والتعارضات والمعاينة/الطباعة.
   - أوامر الاختبار الفعلية ونتائجها: passed/failed/skipped/not run، وأسباب failure/skip. انسخ ملخصات التنفيذ المهمة، ولا تكتب «تم الاختبار» بلا دليل.
   - سجل M01–M18: ما نُفذ وعلى أي وضع/منصة، وما لم يتوفر تنفيذه.
   - قياسات تقريبية لعدد requests في دفعة، وحدود الأداء والقيود المعروفة، خصوصًا JSON concurrency.
   - المشاكل القديمة التي ظهرت ولم تصلحها لأنها خارج النطاق، دون خلطها بانحدارات جديدة.
   - قائمة تحقق نهائية تربط كل معيار قبول بملف/اختبار/دليل.
3. `docs/silent-ui-refresh-codex-review-prompt.md`: **برومبت مراجعة جاهز للمستخدم** مبني على التنفيذ الحقيقي، وليس وعدًا بنجاحه.
4. في ردك النهائي اعرض رابط التقرير ورابط برومبت المراجعة، وانسخ برومبت المراجعة كاملًا إذا كان قصيرًا بما يكفي.

### 18.2 محتوى برومبت المراجعة الذي يجب أن تكتبه بعد التنفيذ

وجّه البرومبت إلى Codex واذكر فيه:

- راجع تنفيذ Gemini في المشروع نفسه وفق هذه الخطة والتقرير الفعليين.
- ابدأ مراجعة فقط؛ لا تصلح الكود أثناء جولة اكتشاف المشاكل إلا إذا طلب المستخدم ذلك.
- هناك تغييرات سابقة وغير متتبعة؛ فرّق تعديلات المهمة عن baseline باستخدام الأدلة التي سجلتها، ولا تنسب كل working tree إلى Gemini.
- اذكر الملفات الفعلية المتغيرة والرموز المهمة ونقاط التركيز، بدون placeholders متروكة أو أسماء اختبارات لم توجد.
- تحقق من جميع الشاشات والتبويبات والمكونات، لا utility وحدها؛ ابحث عن screen-local state التي لم تُوصّل بعد.
- اختبر سوء ترتيب الاستجابات، pending أثناء fetch، فشل الشبكة، pagination/selection/scroll، المسودات وSettings JSON، local/reconnect/resume، الصلاحيات والجلسة، وPDF side effects.
- تحقق من أن listener/تبعيات queries تكفي لتغير المراجع لا جدول Persons/Coming فقط، وأن refresh ownership واحد.
- أعِد الاختبارات المركزة الملائمة، مع إعادة تأكيد منع `flutter analyze` والتحليل الشامل البديل.
- استخدم ملفات التقرير لمعرفة ما نُفذ، لكن تحقق من الكود والاختبارات بنفسك ولا تثق في تقرير النجاح كدليل نهائي.
- أخرج Findings مرتبة P0–P3 مع مسار مطلق وسطر وسبب وسيناريو إعادة إنتاج واقتراح تصحيح، ثم فجوات التغطية والقيود، ثم قرار قبول/رفض واضح مع سببه. إذا لم توجد Findings، صرّح بذلك مع حدود التحقق.
- لا تقل إن المهمة مكتملة لأن بعض الاختبارات نجحت بينما توجد شاشات بلا wiring أو اختبارات مطلوبة لم تُشغّل.

لا تطلب من Codex الاعتماد على ذاكرة المحادثة: يجب أن يكفي البرومبت والملفان داخل المستودع لبدء المراجعة من محادثة جديدة.

## 19. معايير القبول النهائية

- [ ] كل الشاشات الـ27 والمكونات والتبويبات الداخلية لها صف تغطية ودليل مناسب.
- [ ] تغير محلي وتغير بعيد يصلان للواجهة دون حفظ أو تغيير فلتر.
- [ ] البيانات السابقة، بما فيها empty snapshot، تستمر أثناء background request.
- [ ] query/generation/epoch تمنع stale responses وتفصل المستخدم والمصدر ونطاق الوصول.
- [ ] الأحداث أثناء fetch لا تضيع؛ الدفعات والأحداث المستمرة لا تصنع storm أو starvation.
- [ ] لا مسح فلاتر/بحث/فرز/تحديد صالح/صفحات محملة/تمرير بسبب sync.
- [ ] لا overwrite لمسودة أو تحريك focus/cursor أو حفظ تلقائي بإشعار.
- [ ] تغييرات المراجع والروابط والحقول وSettings والصلاحيات تصل لكل مستهلك فعلي.
- [ ] reconnect/resume/إظهار شاشة stale يلتقط التغييرات التي فاتت دون إنشاء اتصالات لكل شاشة.
- [ ] فشل الشبكة يبقي البيانات مع حالة stale وخطأ محدود، ولا يدّعي نجاحًا.
- [ ] لا تكرار نقل/حفظ/حذف/توليد رهوط/طباعة أو إعادة تشغيل scanner/backup.
- [ ] الاختبارات المركزة المناسبة اجتازت، وما لم يُنفذ مسجل صراحة مع أثره على القبول.
- [ ] لم يُشغّل الأمر المحظور أو analyzer شامل بديل، ولم تُلغَ تغييرات المستخدم السابقة.
- [ ] التقرير وبرومبت المراجعة جاهزان ويعكسان العمل الحقيقي والقيود.

## 20. مراجع رسمية للتنفيذ

هذه مراجع APIs والسلوك العام فقط؛ نسخ الحزم المثبتة وكود المشروع هما المرجع لتوقيعات الدوال الفعلية:

- [Drift: Stream queries and manual update notifications](https://drift.simonbinder.eu/dart_api/streams/).
- [Drift: Transactions](https://drift.simonbinder.eu/dart_api/transactions/).
- [Riverpod: Keeping previous data while refreshing](https://riverpod.dev/docs/how_to/pull_to_refresh).
- [Riverpod 3: Lifecycle changes, pause and retry](https://riverpod.dev/docs/whats_new).

المهمة تنجح عندما تظهر البيانات الجديدة بهدوء في الواجهات المعنية مع بقاء شغل المستخدم، وليس بمجرد استقبال socket event أو زيادة عدد `ref.invalidate`.
